Quiero que redactes un `specs.md` para un proyecto de Machine Learning de detección de fraude utilizando el dataset **IEEE-CIS Fraud Detection**.

### Responsabilidad de este archivo

`specs.md` debe definir **qué debe construirse y cuáles son los requisitos concretos del sistema**.

La separación entre documentos es:

* `agents.md` → cómo trabajan los agentes.
* `constitution.md` → principios y reglas innegociables.
* `specs.md` → requisitos, comportamiento esperado, componentes y criterios de aceptación del proyecto.

No repetir innecesariamente contenido de `agents.md` o `constitution.md`.

---

## 1. Objetivo del sistema

Definir un sistema de Machine Learning capaz de estimar si una transacción es fraudulenta utilizando el dataset **IEEE-CIS Fraud Detection**.

El proyecto debe tener orientación de **end-to-end ML Engineering / MLOps**, pero debe desarrollarse progresivamente.

---

## 2. Datos

Especificar el uso de:

* `train_transaction.csv`
* `train_identity.csv`

Definir:

* variable objetivo;
* relación entre ambos datasets;
* identificación de entidades relevantes;
* tratamiento de los datos raw;
* requisitos de validación y calidad;
* separación entre datos de desarrollo y evaluación.

El agente debe investigar la estructura real del dataset antes de fijar detalles que no estén confirmados.

---

## 3. Data understanding y EDA

Definir como requisito realizar un análisis que permita conocer:

* tipos de variables;
* missing values;
* cardinalidad;
* distribuciones;
* variables categóricas y numéricas;
* distribución de fraude;
* comportamiento temporal;
* relaciones relevantes entre variables;
* posibles anomalías o inconsistencias.

El EDA debe producir conclusiones que sirvan como fundamento para decisiones posteriores de preprocessing y feature engineering.

---

## 4. Preprocessing

Definir los requisitos para construir un pipeline reproducible de preprocessing.

Debe contemplar, según lo que determine el análisis:

* tratamiento de missing values;
* variables categóricas;
* variables numéricas;
* encoding;
* scaling cuando sea necesario;
* eliminación o conservación justificada de variables;
* transformaciones reproducibles.

Las transformaciones deben poder reutilizarse durante inferencia.

No fijar de antemano transformaciones específicas cuando estas deban determinarse a partir del EDA.

---

## 5. Feature engineering

Definir un componente específico de feature engineering.

Debe contemplar la posibilidad de crear features relacionadas con:

* tiempo;
* frecuencia;
* comportamiento histórico;
* importes;
* entidades;
* relaciones entre entidades;
* comportamiento relativo de una transacción respecto al historial.

Para cada feature relevante deberá poder conocerse:

* qué representa;
* cómo se calcula;
* qué información utiliza;
* si está disponible en el momento de inferencia.

Prestar especial atención a features temporales y agregaciones históricas.

---

## 6. División de datos

Definir una estrategia de train/validation/test adecuada para un problema transaccional y temporal.

La estrategia debe evitar que información futura termine influyendo en el entrenamiento.

Debe quedar especificado:

* cómo se generan los conjuntos;
* cuándo se utiliza cada uno;
* cómo se mantiene aislado el test;
* cómo se garantiza la reproducibilidad.

---

## 7. Modelado

Definir una estrategia progresiva:

1. baseline;
2. modelos clásicos;
3. modelos de boosting;
4. tuning de hiperparámetros cuando corresponda.

El sistema debe permitir comparar distintos experimentos bajo condiciones equivalentes.

No asumir que un modelo específico será necesariamente el definitivo.

---

## 8. Evaluación

Definir un sistema de evaluación adecuado para fraude y clases desbalanceadas.

Debe contemplar métricas como:

* precision;
* recall;
* F1;
* ROC-AUC;
* PR-AUC;
* matriz de confusión.

También debe contemplarse el análisis de diferentes thresholds de clasificación.

El test set debe utilizarse únicamente para la evaluación final correspondiente.

---

## 9. Explainability

Definir requisitos para poder analizar por qué el modelo realiza sus predicciones.

Considerar herramientas como:

* feature importance;
* SHAP u otra técnica apropiada.

La solución debe permitir estudiar tanto el comportamiento global como predicciones individuales cuando sea posible.

---

## 10. Experiment tracking

Definir integración con **MLflow** para registrar:

* experimentos;
* parámetros;
* métricas;
* modelos;
* artefactos relevantes.

Los experimentos deben poder reproducirse y compararse.

---

## 11. Inferencia

Definir una etapa de inferencia que:

* reciba una nueva transacción;
* aplique exactamente las transformaciones necesarias;
* genere una probabilidad de fraude;
* aplique un threshold configurable;
* devuelva una predicción interpretable.

La lógica utilizada para preprocessing y feature engineering debe ser consistente entre entrenamiento e inferencia.

---

## 12. API y empaquetado

Definir posteriormente una API de inferencia utilizando una tecnología apropiada, por ejemplo **FastAPI**.

La API debe permitir:

* recibir datos de una transacción;
* ejecutar preprocessing;
* ejecutar el modelo;
* devolver resultado y probabilidad.

La implementación concreta puede definirse durante las tareas correspondientes.

---

## 13. Docker y MLOps

Definir como evolución del proyecto:

* Docker;
* tests automatizados;
* CI/CD;
* MLflow;
* monitoring.

No es necesario implementar todos estos componentes inicialmente.

El desarrollo debe ser incremental y cada componente debe incorporarse cuando las etapas anteriores estén suficientemente establecidas.

---

## 14. Estructura conceptual

El sistema completo debería evolucionar aproximadamente según:

`Raw Data → Validation → EDA → Preprocessing → Feature Engineering → Split → Training → Evaluation → Explainability → MLflow → Inference → API → Docker → Monitoring`

La estructura final de carpetas y archivos no debe fijarse arbitrariamente en este documento si todavía no se ha tomado esa decisión.

---

## 15. Criterios de aceptación

Definir criterios verificables para considerar completadas las principales etapas.

Por ejemplo:

* los datos pueden validarse;
* el preprocessing es reproducible;
* las features pueden generarse consistentemente;
* no existe leakage conocido;
* el modelo puede entrenarse reproduciblemente;
* las métricas pueden calcularse;
* los experimentos quedan registrados;
* una nueva transacción puede atravesar el pipeline completo;
* la inferencia utiliza el mismo procesamiento que el entrenamiento.

Los criterios deben ser concretos y comprobables.
